# LYRICLAB — 歌詞コライトのスプリット管理

SPLITAPP（SPLITLAB）の派生版。仕組み・デザインシステムはそのまま流用しつつ、
**アプリの中で作詞し、その作業ログから貢献パーセンテージを算出する** ところが違う。

- SPLITAPP … 制作ログを後から手入力 → AIで分析
- LYRICLAB … アプリ内の作詞操作そのものがログになる → ログから自動算出

## 起動

`start_server.bat` をダブルクリック（http://127.0.0.1:8010/index.html が開く）。
データはブラウザの localStorage に保存される。

## 3つのモード（Googleドキュメント風）

| モード | 挙動 | 記録 |
|---|---|---|
| ✎ 編集 | 行をクリックして直接書き換え | 増えた文字数がその人のクレジットになる |
| ✍ 提案 | 書き換え案・追加案・削除案を出す | 相手が「採用」したときだけ歌詞に反映。提案者の貢献になる |
| 💬 コメント | 行・セクションに指摘や質問を残す | 歌詞は変わらないが推敲への関与としてログに残る |

提案とコメントは右のサイドパネルで一覧・採用/却下・返信・解決ができる。

## 画面レイアウト

### 広い画面（1024px〜）— 3カラム固定

```
歌詞エディタ ｜ 歌詞プレビュー（主役・中央） ｜ サイドパネル（提案・コメント・ログ・分析）
```

- **画面いっぱい**に広げる（案件画面のみ最大幅の制限を外す。案件一覧は72remのまま）
- **ページ自体はスクロールしない**。スクロールするのは各カラムの中身だけ（歌詞リスト／プレビュー／パネル）
- 既定の比率は プレビュー 1.6 : エディタ 1.15 : パネル 0.85
- カラムの境目を**ドラッグして幅を調整**できる。掴んだ2カラムの間だけで幅を配分するので反対側は動かない。最小幅220px、**ダブルクリックで既定に戻す**、比率は端末に保存

### 狭い画面（〜1023px）— 1カラム

縦積みの通常スクロールに戻る。見失わないよう、画面上部に追従バー（現在の比率＋歌詞／プレビュー／提案・分析へのジャンプ）とセクション見出しの貼り付きが有効になる。

| その他の工夫 | 内容 |
|---|---|
| ログの初期表示 | 作業ログは最新25件のみ。ボタンで全件表示に切り替え |
| 読み幅の制限 | プレビューの歌詞は42remまで。全幅に流して視線移動が長くなるのを防ぐ |

プレビュー列は「隠す」でたためる（エディタ下の「プレビューを表示」で復帰）。

### エディタとプレビューの役割分担

エディタとプレビューは統合していない。編集中に完成形が崩れないよう分けたうえで、
**エディタ側を「読める見た目」に寄せる**ことで実質的に統合と同じ体験を狙っている。

エディタ上部の表示トグル（設定は端末に保存）:

| トグル | 内容 |
|---|---|
| すっきり表示 | 行番号・セクション種別・比重・削除ボタンを、その行／セクションにホバーしたときだけ出す。行間も広がり歌詞が素直に読める。提案・コメントのバッジは「今の状態」なので常に表示 |
| 作者色分け | 行の左罫を主著者の色にする。オフで完全に無地 |

プレビュー列の役割は2つに絞ってある:

| モード | 内容 |
|---|---|
| 完成形 | 今の歌詞を通しで読む・清書のコピー |
| 提案を反映 | 未処理の提案をすべて反映した姿。元の行は取り消し線、提案は緑で表示 |

「コピー」は表示中のモードのまま書き出す（提案反映モードでは `-` / `+` 付き）。

## 多段階AI判定

SPLITAPP と同じ「機械集計 → AI判定 → 統合」の積み上げ方式。分析タブの「AIで分析」から実行し、段ごとに進捗が出る。

| 段 | 内容 | AI |
|---|---|---|
| 1 | 機械集計 | 不要（文字の持ち分・提案採用・関与ログ） |
| 2 | 歌詞的比重 | あり。歌詞本文を読み、作品の核となる言葉を誰が書いたかを判定 |
| 3 | 5軸評価 | あり。同一性／影響範囲／役割／採用度／代替不可能性を軸ごとに採点 |
| 4 | 統合 | 機械45% ＋ 歌詞的比重40% ＋ 5軸15% |

AIには歌詞本文に加えて、行ごとの執筆者と文字数、セクション種別と比重、提案の採否履歴を渡す。結果は案件に保存され、貢献レポートにも出力される。「合意の初期値にする」で合意モーダルへ流し込める。

### 接続方法（どちらか）

1. **Apps Script経由**（推奨・SPLITAPPと同じ運用／同期と共用）
   `apps-script/Code.gs` をデプロイし、Script Properties に `API_KEY` と `GEMINI_API_KEY` を設定。アプリ側にURLと接続キーを入力。キーがブラウザに出ない。
2. **Gemini APIキー直接**
   キーを直接入力してブラウザから呼ぶ。手軽だが共有PCでは非推奨。

URLとモデル名は localStorage、キーは **sessionStorage**（タブを閉じると消える）に保存。

## スプレッドシート同期

SPLITAPP と同じく、Google スプレッドシートをデータベースにする。**AI分析と同じウェブアプリ・同じ接続キー**を使う（ヘッダーの同期ピルから設定）。

### 起動時の接続

SPLITAPP と同じく、**まず接続してから使う**。未接続の状態で起動すると入口に接続画面が出る。

- URLは localStorage に残るので、2回目以降は接続キーを入れるだけで戻れる
- 「接続して開く」は保存前に実際に `pull` を投げて確認する。打ち間違いのまま編集を始めることがない
- 接続に成功すると、そのまま自動で同期して最新を取り込む
- 接続キーは sessionStorage なので、タブを閉じると未接続に戻る（開くたびに入力）
- 「接続せずにこの端末だけで使う」も選べる。この端末の localStorage にある案件だけを開き、共作者とは共有されない（タブを閉じるまで有効）

- ヘッダーの「同期」ボタンで手動同期。ピルに 未接続 / 接続済み / 同期中 / 同期エラー / 最終同期時刻 が出る（エラー理由はピルのツールチップ）
- 双方向：リモートを取得 → `updatedAt` が新しい方を採用 → ローカルが新しい案件だけ送信
- 案件データは入れ子が深いので列に展開せず、`dataJson` にJSONのまま格納。`id` / `title` / `updatedAt` だけ列に持たせて一覧と差分判定に使う
- **セルの5万文字制限があるため、`dataJson` は4万文字ごとに分割して複数行に保存する**。同じ `id` の行を `chunk` 列の番号順に連結して1件に戻す（`chunks` は総数）。案件は作業ログを全部持つので、ログ200件強で5万字に届く。分割しないと `setValues` がそこで失敗する
- 旧5列（`chunk` / `chunks` なし）のシートは、見出しを足すだけで移行できる。既存行は `chunk` が空になるが、1枚ものとして読める
- 削除は行を消さず `deleted` フラグ（誤操作からの復旧用）
- 書き込みは `LockService` で排他

### 準備

1. スプレッドシートを作り、URLの `/d/` と `/edit` の間のIDを控える
2. Apps Script に `apps-script/Code.gs` を貼り、スクリプト プロパティに `SHEET_ID` と `API_KEY`（AIも使うなら `GEMINI_API_KEY`）を登録
3. エディタから **`setupDatabase` を1回実行**してシートを作成
4. ウェブアプリとしてデプロイ（実行ユーザー: 自分／アクセス: 全員）
5. `/exec` で終わるURLと接続キーをアプリの「接続設定（AI・同期）」に入力

### 接続できないとき

ブラウザのコンソールに `has been blocked by CORS policy` と出る場合、**リクエストが `doPost` に届いていない**。Apps Script がログイン画面へリダイレクトしており、そのリダイレクト先に CORS ヘッダが無い、というのが実体。`Code.gs` は例外もJSONで返すので、コード側のエラーならCORSにはならない。

確認する順に:

1. **デプロイ > デプロイを管理 > アクセスできるユーザー** が「**全員**」になっているか。「Googleアカウントを持つ全員」や「自分のみ」だとログインが要求され、ブラウザからは必ず失敗する
2. コードを更新した場合、**新しいバージョンとしてデプロイし直したか**。既存デプロイの編集画面で「バージョン: 新バージョン」を選ぶ必要がある
3. URLが `/exec` で終わっているか（`/dev` はログイン必須のテスト用）
4. Google Workspace アカウントの場合、管理者設定で外部共有が禁止されていると「全員」を選べないことがある。その場合は個人アカウントでデプロイする

> 現状は**手動同期のみ**。自動同期・削除の伝播・複数人同時編集の競合解決（今は updatedAt の新しい方を丸ごと採用）は未実装。

## 作業者の自動判別（端末ひも付け）

ログインもパスワードも持たない。**「この端末は誰のものか」を一度だけ決めて覚える**方式。

- 初回に名前を1回入力すると、以降その端末での操作は自動でその人として記録される
- 案件ごとに共作者IDは別なので、端末側に「案件 → 自分の共作者ID」の対応表（`lyriclab_device`）を持つ
- 別端末で作られた案件を開いたときは、**同じ名前の共作者を自動で照合**して対応表に追加する
- 決まらないときだけ「この案件でのあなた」を選ぶダイアログが出る。一覧にいなければ「新しい共作者として参加する」で自分を追加できる
- 新規案件を作ると、1人目の共作者が自動でその端末の持ち主の名前になる
- ヘッダーの 👤 からいつでも変更できる

### 取り違えの防止

- 作業ログには作業者IDに加えて**端末ID・端末名**も残る（後から名義の取り違えを追える）
- ヘッダーの作業者を手動で切り替えると **「別名義（本来は◯◯）」** バッジが出る。クリックで自分に戻る。手動切り替えでは端末のひも付け自体は変わらない

> これは「取り違えない」ための仕組みであって、本人証明ではない。証明が必要になったら（＝スプリット交渉で証拠能力を求める段階になったら）、端末に保存する名前をGoogleアカウントのメールアドレスに置き換え、Apps Script側で検証する形に拡張できる。データ構造は変えずに済む。

## セクションの呼び名（J-POP方式 / 洋楽方式）

歌詞エディタ右上の「セクションの呼び名」で切り替える（選択は端末に保存）。

| 種別 | J-POP方式 | 洋楽方式 | 比重 |
|---|---|---|---|
| intro | イントロ | Intro | ×0.70 |
| verse | Aメロ | Verse | ×1.00 |
| prechorus | Bメロ | Pre-chorus | ×1.15 |
| chorus | サビ | Chorus | ×1.50 |
| finalchorus | 大サビ | Final chorus | ×1.60 |
| quietchorus | 落ちサビ | Quiet chorus | ×1.40 |
| hook | フック | Hook | ×1.40 |
| bridge | Cメロ | Bridge | ×1.20 |
| interlude | 間奏 | Interlude | ×0.60 |
| rap | ラップ | Rap | ×1.10 |
| outro | アウトロ | Outro | ×0.80 |
| other | その他 | Other | ×1.00 |

- 自動命名のセクションは切り替えに追従する（同じ種別が複数あるときだけ `Aメロ1 / Aメロ2`、`Verse 1 / Verse 2` と連番）
- セクション名を手で書き換えるとその名前で固定される（例：「回想」）。**名前を空にすると自動命名に戻る**
- 一括入力は `[Aメロ]` `[大サビ]` でも `[Verse 1]` `[Chorus]` でも種別を自動判定。定型名は自動命名に、独自の見出しは名前として保持

## 貢献パーセンテージの算出

`app.js` の `analyze()` が3軸を配合する。データのない軸の配合比は自動的に他の軸へ按分される。

1. **現存する歌詞（55%）**
   完成歌詞に *今も残っている* 文字を書いた人ごとに集計。
   行が書き換えられると、増えた文字は編集者へ、消えた文字は既存クレジット全体から按分して削る
   （`applyCredits()`：共通の先頭・末尾を除いた差分だけを見る単純ルール）。
   セクション比重（大サビ ×1.6 / サビ ×1.5 / 落ちサビ ×1.4 / Cメロ ×1.2 / Aメロ ×1.0 …）を掛ける。
2. **採用された提案（20%）**
   提案モードで出し、相手が採用した案。文字数 × セクション比重 × 0.5 ＋ 採用ボーナス。
3. **推敲・レビュー関与（25%）**
   作業ログの手数（`LOG_TYPES` のポイント）。歌詞に文字として残らない貢献を拾う軸。

算出値はあくまで参考値。「スプリット合意」から最終比率を手入力して確定できる（合計100%必須）。

## セキュリティとプライバシー

このリポジトリに含まれるのは**コードだけ**。歌詞・作業ログ・比率などのデータは一切入っていない
（データはブラウザの localStorage と、各自が用意するスプレッドシートにしか存在しない）。
APIキーや接続URLもコードには持たず、すべて実行時にユーザーが入力する。

### 鍵の扱い

| 項目 | 保存先 | 備考 |
|---|---|---|
| Apps Script URL / モデル名 | localStorage | 秘密ではないが接続先が分かる情報 |
| 接続キー・Gemini APIキー | **sessionStorage** | タブを閉じると消える。リポジトリにも同期先にも送らない |
| 端末の名前・端末ID | localStorage | 端末ひも付け用。個人特定情報は入れない想定 |

### 運用上の注意

- **Apps Script を「アクセスできるユーザー: 全員」でデプロイすると、そのURLは公開エンドポイントになる。**
  保護は `API_KEY` という共有シークレット1つだけなので、十分長いランダム文字列にすること。
  URLとキーの両方が漏れると、全案件の読み書きが可能になる。漏れたらキーを差し替えて再デプロイする。
- **AI分析は歌詞の本文を Google（Gemini API）へ送信する。** 未発表の歌詞を外部に送ることになる点は理解した上で使うこと。使わなければ送信は発生しない。
- **Gemini APIキー直接モードはブラウザにキーが載る。** 共有PCでは Apps Script 経由を使うこと。
- 同期で受け取った案件は、IDが英数字とハイフンのみか・色が16進カラーかを検証してから取り込む（属性へ差し込まれる値の細工を防ぐため）。検証を通らない案件は取り込まずスキップ数を通知する。
- 画面に出るユーザー入力（歌詞・コメント・提案・共作者名）はすべてHTMLエスケープしてから描画している。
- **端末ひも付けは本人証明ではない。** localStorage は書き換えられるので、「取り違え防止」以上の意味は持たない。
